# Issue Tracker Workflow

How issues flow on `stonematt/lookout`. Optimised for one-maintainer
operation with AI agents doing spec authoring, triage assistance, and
implementation.

Issues, specs and tickets live as **GitHub issues** at `stonematt/lookout`. Use the
`gh` CLI for all operations — `gh` infers the repo from `git remote -v`
when run inside a clone.

## Label vocabulary

Every triaged issue carries **exactly one category label** and **exactly
one state label**. The maintainer can override at any time.

### Categories

| Label         | Meaning                          |
|---------------|----------------------------------|
| `bug`         | Something is broken              |
| `enhancement` | New feature or improvement       |
| `refactor`    | Deepening refactor from an architecture review; its spec and tickets keep the label |

### States

| Label              | Meaning                                                |
|--------------------|--------------------------------------------------------|
| `needs-triage`     | Maintainer hasn't evaluated yet                        |
| `needs-info`       | Waiting on reporter for more information               |
| `ready-for-agent`  | Fully specified, an AFK agent can pick it up           |
| `ready-for-human`  | Fully specified, requires human (judgment / external)  |
| `wontfix`          | Won't be actioned                                      |

State machine:

```
(unlabeled new issue)
        ↓
   needs-triage
        ↓
   ┌────┴───────────────────────────────┐
   ↓        ↓               ↓          ↓
needs-info  ready-for-agent  ready-for-human  wontfix → closed
   ↓
   (reporter replies → back to needs-triage)
```

## Lifecycle

### 1. Create

Issues land via:

- **Reporter form** (Web UI / API) — usually starts as a bug report or
  feature request.
- **Direct `gh issue create`**, e.g. an architecture-review candidate
  filed as a `refactor` brief. Lands with `needs-triage`.
- **`/grill-with-docs` then `/to-spec`**: a grilled issue becomes a spec.
  The issue body is replaced by the spec, the original brief moves to the
  first comment, and the label goes `needs-triage` → `ready-for-agent`.
- **`/to-tickets`** on a spec: see [Vertical slicing](#4-vertical-slicing).
  Tickets land `ready-for-agent` with the spec's category label.

Everything else lands with `needs-triage`.

### 2. Triage

Run `/triage` (loads `~/.claude/skills/triage`). The skill knows the
canonical role names; the labels above are the local mapping.

Outputs of triage:

- `ready-for-agent` — post an **agent brief** comment on the issue (see
  [the triage skill's AGENT-BRIEF.md](../../../../.claude/skills/triage/AGENT-BRIEF.md)
  in your home install). The brief is the contract the AFK agent works
  from; the issue body is context.
- `ready-for-human` — same shape as an agent brief, but note why a human
  has to do it (judgment, external access, manual testing).
- `needs-info` — comment using the triage skill's needs-info template.
- `wontfix` (enhancement) — write to `.out-of-scope/<concept>.md`,
  link from a closing comment.
- `wontfix` (bug) — close with explanation.

### 3. Implementation

For `ready-for-agent` issues: an AFK agent picks the work up, branches,
implements, opens a PR. A ticket's body is its brief; its parent spec is
the context. A triaged issue's agent brief comment is its brief.

For `ready-for-human`: maintainer or human contributor handles directly.

### 4. Vertical slicing

Run **`/to-tickets`** on a spec to break it into vertical slices. Each
ticket is its own `ready-for-agent` issue, attached to the spec as a
native **sub-issue**, with native **blocked-by** links to the tickets that
gate it (commands under [Wayfinding operations](#wayfinding-operations)).
The spec stays open until its tickets close.

**A spec is ticketed** when its sub-issue list is non-empty:
`gh api repos/stonematt/lookout/issues/<spec>/sub_issues --jq length`.
Check this, not issue search: search does not match `#<number>` text.

## AI-generated comments

Per the triage skill, every comment posted by `/triage` **must** start
with this disclaimer (specs and tickets do not carry it):

```
> *This was generated by AI during triage.*
```


## Domain glossary

When writing specs, tickets, agent briefs, or issue comments, use the canonical
domain vocabulary from [GLOSSARY.md](../../GLOSSARY.md). Don't invent new
terms. If a term needs sharpening, do it in GLOSSARY.md, then reference
it from the issue.

## ADR cross-references

Decisions affecting an area should reference the relevant ADR in
`docs/adr/`. Agent briefs in particular should call out applicable ADRs
so the implementing agent doesn't relitigate settled decisions.

## Wayfinding operations

How `/wayfinder` maps live on this tracker. Wayfinder issues carry only
`wayfinder:*` labels, never a category or triage-state label: they are
decisions, not implementation work, so `/triage` skips them.

- **Map**: one issue labelled `wayfinder:map`.
- **Tickets**: issues labelled `wayfinder:research`, `wayfinder:prototype`,
  `wayfinder:grilling` or `wayfinder:task`, attached to the map as native
  sub-issues. The sub-issue API takes the issue's database `id`, not its
  number:
  `gh api -X POST repos/stonematt/lookout/issues/<map>/sub_issues -F sub_issue_id=$(gh api repos/stonematt/lookout/issues/<ticket> --jq .id)`
- **Blocking**: native issue dependencies, also keyed by database `id`:
  `gh api -X POST repos/stonematt/lookout/issues/<blocked>/dependencies/blocked_by -F issue_id=$(gh api repos/stonematt/lookout/issues/<blocker> --jq .id)`
- **Claim**: assign the ticket before any work:
  `gh issue edit <ticket> --add-assignee @me`
- **Frontier**: open, unassigned sub-issues with no open blockers.
  `issue_dependencies_summary.blocked_by` counts open blockers only:
  `gh api repos/stonematt/lookout/issues/<map>/sub_issues --jq '.[] | select(.state=="open" and (.assignees|length)==0 and .issue_dependencies_summary.blocked_by==0) | "\(.number) \(.title)"'`
- **Resolve**: post the answer with `gh issue close <ticket> --comment "..."`,
  then append one line to the map body's `## Decisions so far` via
  `gh issue edit <map> --body-file`.
- **Research findings** go on a pushed `research/<name>` branch that is
  never merged and has no PR. The resolution comment links the file.

## `gh` CLI cheat sheet

Shorthand for the verbs the workflow above uses.

- **Create an issue**: `gh issue create --title "..." --body "..."`. Use a heredoc for multi-line bodies.
- **Read an issue**: `gh issue view <number> --comments`, filtering comments by `jq` and also fetching labels.
- **List issues**: `gh issue list --state open --json number,title,body,labels,comments --jq '[.[] | {number, title, body, labels: [.labels[].name], comments: [.comments[].body]}]'` with appropriate `--label` and `--state` filters.
- **Comment on an issue**: `gh issue comment <number> --body "..."`
- **Apply / remove labels**: `gh issue edit <number> --add-label "..."` / `--remove-label "..."`
- **Close**: `gh issue close <number> --comment "..."`

### When a skill says "publish to the issue tracker"

Create a GitHub issue.

### When a skill says "fetch the relevant ticket"

Run `gh issue view <number> --comments`.
